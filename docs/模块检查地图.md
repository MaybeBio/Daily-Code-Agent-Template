# Daily-Code-Agent-Template 模块检查地图

按**功能实现顺序**编排的逐阶段检查地图:每个阶段**实现什么功能**、**检查什么**、**用哪些脚本及各自用途**。

---

## 一、总览:数据流水线

```
每日(daily.yml)   →  scripts/daily.py            → monitor/**/*.txt + data/daily/*.repos.json
每周(weekly.yml)  →  scripts/run_weekly.sh:
   ① search   → search.py  + gh.py            → data/search/<date>.json
   ② merge    → merge.py   + registry.json      → data/candidates/<date>.json
   ③ score    → score.py   + agent.py + prompts → data/scored/<date>.json + registry.json
   ④ archive  → archive.py (degit/repowiki-cli) → code/<owner__repo>/ + data/archive/<date>.json
   ⑤ cards    → cards.py   + agent.py + prompts → data/cards/<date>.json
   ⑥ issue    → issue.py                        → data/weekly/<date>.csv + /tmp/issue.md
站点(deploy_pages.yml) → build_site.py + templates/ → site/ → GitHub Pages
```

**贯穿所有阶段的两个底层模块**
- `scripts/common.py` — 路径与配置的单一真源:`ROOT` / `load_config` / `data_dir(kind,file)`(统一产出 `data/<kind>/<file>`)/ `dump_json`/`load_json` / `today` / `read_registry`(读 `data/registry.json`)/ **`topic_brief(cfg)`**(按 `topic_desc`→`title`→`topic` 取人类可读课题说明,喂 LLM 用,score 与 cards 都调它)。
- `scripts/logs.py` — 纯解析器,把 ghresearcher 的多行事件文本拆成结构化事件:`unwrap_records`(按时间戳拼多行)→ `parse_event`(emoji/动词→事件类型,锚定动词后第一个 `owner/repo`)→ `extract_events` → `repos_from_events`(按仓库聚合 who/kinds)。**无网络、无副作用,最好单测**。

## 二、每日阶段 / Daily feed

| 项 | 内容 |
|---|---|
| 入口 | `.github/workflows/daily.yml`(`workflow_dispatch`,外部 cron 触发) |
| 脚本 | `scripts/daily.py`(主) 调 `gh.py` / `logs.py` / `common.py` |
| 功能 | 拉 3 个 watchlist 的免费元数据流,做**不调用 LLM** 的候选仓库表,提交并开 Issue |
| 产出 | `monitor/{users,orgs,received}/YYYY/MM/DD.txt`(原始)+ `data/daily/<date>.repos.json`(结构化)+ Issue |

**实现细节(daily.py)**
- `collect()`:对 `users` / `orgs`(`--org`)/ `users_core`(`-r -l 30`,received 流)分别跑 `ghresearcher monitor -f <list> --since <昨天> --expand-commits`;每个 list 失败只 `continue`(不炸整体);再用 `logs` 聚合出候选,逐个 `gh.safe_repo_meta` 补 stars/language/description/url,按 stars 降序。
- `build_daily_issue()`:标题 `📡 每日动态 <date> · <title>`;表头 `repo | 谁 | 事件 | stars | language | description`;description 里的 `|` 转义。

**检查什么**
1. `users_core.txt` 是否为 `users.txt` 的**真子集**(CLAUDE.md 的硬约束,否则 received 流会引入非预期用户)。
2. `--since` 用的是"昨天"(daily 语义),与 weekly 的 7 天窗口不同 —— 别混淆。
3. 表头 6 列 vs 行 6 列对齐(`test_daily.py` 应覆盖);`description` 含 `|` 时是否被转义。
4. 单个 watchlist 失败时是否只跳过而非整体失败。

## 三、每周阶段 / Weekly pipeline(`run_weekly.sh`,6 步,`set -euo pipefail`)

### ① search — 发现

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/search.py` + `scripts/gh.py::search_repos` |
| 输入 | `config.yaml → search.queries`(9 条短语查询)+ `queries/search_repos.yaml`(纯 gh 参数) |
| 产出 | `data/search/<date>.json` |
| 功能 | 逐条查询 → Union 后按 `full_name` 去重 |

**实现(重点)**
- `_queries()`:优先用 `config.yaml` 的 `search.queries` 列表;无则回退读 yaml 里的单 `query`。
- 对每条 query 调 `gh.search_repos(qcfg, since, FIELDS, query=query)`,后者拼 `ghresearcher search repos "<query>" --config ... --updated ... --json ...`;归一化后 `merged[full_name]=n` 覆盖去重。
- `FIELDS = [fullName,url,language,stargazersCount,description,pushedAt]`。

**检查什么(最容易踩坑的一步)**
1. `queries/search_repos.yaml` 里**只能有合法 gh flag**;多写 `query/queries` 会被 ghresearcher 透传成 `--queries` 报 `unknown flag`。
2. 不要用 `A OR B in:`(in: 只绑最后一个词)或裸缩写 IDR/IDP(子串命中外语词,噪声炸裂)。当前 9 条都是"引号短语 + in:name,description,topics",符合规则。
3. 去重键是 `full_name`;确认 `pushed_at` 被带入(merge 阶段要靠它判 new/updated)。

### ② merge — 分流

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/merge.py`(读 `data/daily/*`、`data/search/*`、`registry.json`) |
| 产出 | `data/candidates/<date>.json`;`seen` 列表 |
| 功能 | 近 `window_days` 天的 daily + 本次 search 汇成池 → 分类 new / updated / seen |

**实现**:`_recent_daily` 取窗口内文件;池内 `setdefault` 去重;search 的 `pushed_at` 优先补全;`classify()`:registry 无记录→`new`,有记录且 `pushed_at != last_commit`→`updated`,否则→`seen`(seen 直接丢弃,不再打分)。缺 `pushed_at` 的用 `safe_repo_meta` 补。

**检查什么**
1. `classify` 的比较字段必须与 score 阶段写入 registry 的 `last_commit` 一致(当前都用 `pushed_at`)。
2. seen 的语义:**去重"本周已见过且无更新"的仓库**,是 README open-question 里"跨周去重"的落点 —— 确认这是预期而非误杀。
3. 窗口边界:`>= cutoff` 是否包含当天。

### ③ score — 打分

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/score.py` + `scripts/agent.py::score_repo` + `prompts.yaml(score)` |
| 产出 | `data/scored/<date>.json`;回写 `data/registry.json` |
| 功能 | 拉 README,LLM 按三轴 rubric 判相关性,并发打分 |

**实现**:`_score_one` 取 README → `agent.score_repo(client, model, prompts, common.topic_brief(cfg), readme)`;ThreadPoolExecutor(`llm.concurrency=8`);registry 记 `first_seen/last_seen/last_commit/last_scored_commit/score/one_liner`。

**检查什么**
1. `topic_brief(cfg)` 必须传**人类可读说明**而非 slug(`test_score.py::test_run_passes_topic_brief_not_slug`)。
2. prompt 的 `user:` 模板只含 `{topic}`/`{readme}`;system 里的字面 JSON 花括号**绝不能**被 `.format()` —— 否则 KeyError。
3. rubric 三轴(对象/领域/形态)分档 8-10 / 5-7 / 0-4 与 `llm.min_score=5` 门限一致(50+ 噪声是否被压到 0-4)。
4. 单条失败重试与兜底分数是否合理,不会把整批拖垮。

### ④ archive — 克隆 + wiki 归档

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/archive.py` |
| 产出 | `code/<owner__repo>/{code/, deepwiki/, zread/, google_code_wiki/}` + `data/archive/<date>.json` |
| 功能 | 对 score ≥ min_score 的 keeper:`degit` 浅克隆 + 三源 wiki 导出 |

**实现**:`threshold()` 取 keeper 按分降序;`_run_retry(cmd, tag, attempts=3)` 指数退避,失败 stderr 记 `[tag failed]`;`clone_repo`=`degit <repo> <dest> --force`;`export_wiki`=`repowiki-cli <src> cp <repo> <dest>`;`repo_dir` 把 `/`→`__`;`_wiki_dir` 把 codewiki 映射到 `google_code_wiki`;ThreadPoolExecutor(`archive.concurrency=4`,低并发防 repowiki 限流);`_safe_archive_one` 捕获异常,单仓库失败不炸整批。

**检查什么**
1. `code/` 目录名映射与 `build_site.repo_dir_name`(也是 `/`→`__`)必须一致,否则网页连不到克隆。
2. `WIKI_SOURCES=["deepwiki","codewiki","zread"]` 与目录映射、与 build_site 的 `wiki_url` 三处对齐。
3. 已知环境问题:`repowiki-cli` 在本机是断链符号链接(exit 127);`degit idptools/afrc` 是确定性失败 —— 都要靠 `_run_retry` + 日志区分"重试可救"与"根本失败"。
4. wiki **不可增量更新**(README open-question):重跑会 `rmtree` 整目录重拉,确认可接受。

### ⑤ cards — 生成富卡片

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/cards.py` + `scripts/agent.py::build_code_card` + `prompts.yaml(code_card)` |
| 产出 | `data/cards/<date>.json`(9 键记录) |
| 功能 | 对 keeper 生成 4 段式 Markdown 卡片,供站点渲染 |

**实现**:复用 `archive.threshold` 只留 keeper;`work()` 调 `build_code_card(..., common.topic_brief(cfg), readme)`,失败 stderr 记 `[card failed]`;`card_record()` 组 9 键;`run()` 写 cards。

**检查什么**
1. keeper 门限与 archive **完全同源**(都走 `archive.threshold` + `llm.min_score`),否则站点会缺卡或多卡。
2. 4 个固定 `##` 小节结构 + 反臆测 guard 是否稳定(模板漂移会让卡片风格不齐)。
3. `data/cards/*.json` 的记录字段与 `build_site.build_site` 读取的键(`full_name/card/score/...`)匹配。

### ⑥ issue — 汇总推送

| 项 | 内容 |
|---|---|
| 脚本 | `scripts/issue.py` |
| 产出 | `data/weekly/<date>.csv`(8 列)+ `/tmp/issue.md`(7 列 markdown 表) |
| 功能 | 分组(new/updated)按分排序 → Issue 正文 + CSV |

**实现**:标题 `🔍 每周仓库发现 <end> · <n_new> 新增 / <n_upd> 更新`;`_section` 表头 `repo | language | stars | last_commit | status | score | one_liner`;`write_csv` 仍写含 `url` 的 8 列。

**检查什么**
1. **CSV 8 列 vs 表头 7 列**是刻意差异(CSV 要 url,表格不要)—— `test_issue_table_columns_match_header` 校验表头与行竖线数相等。
2. 分组顺序 新增 在 更新 之前,组内按 score 降序 → 但 Issue 正文/CSV 目前含**全部 scored(含 0 分噪声)**,这是悬而未决的 **P5 产品决策**(keeper/all 是否拆分)。

## 四、站点阶段 / Site(`deploy_pages.yml → build_site.py → templates/`)

| 项 | 内容 |
|---|---|
| 触发 | `workflow_run`(weekly 成功完成后)+ `workflow_dispatch` 双触发(手动推 gitignored `site/` 不触发 workflow_run) |
| 脚本 | `scripts/build_site.py` + `templates/{base,index,code,archive,_code_card}.html` + `assets/style.css` |
| 产出 | `site/`(gitignored,部署时重建) |
| 功能 | 走 `data/cards/*.json`,渲染首页(本周卡片)+ 每仓库独立页 + 归档页 |

**实现**:`load_cards` 按日期降序读所有 cards;`load_issue_url` 读 `data/latest_issue.txt`(由 weekly.yml 开 Issue 后写入);`score_tier`(≥8 high/≥5 mid)、`wiki_url`、`repo_dir_name` 注册为 Jinja globals;`code.html` 逐仓库渲染到 `site/repos/<owner__repo>/index.html`;`index.html`/`archive.html` 汇总;`site_base_path` 解析 `site_base_url` 供子路径部署。

**检查什么**
1. `wiki_url` 的 deepwiki/codewiki/zread URL 是否与归档目录名(尤其 codewiki→google_code_wiki)对得上。
2. `latest_issue.txt` 缺失时(首次跑、开 Issue 失败)页面是否优雅降级(`load_issue_url` 返回 `""`)。
3. `repo_dir_name` 与 archive 的 `repo_dir` 命名一致性(同一 `/`→`__` 规则)。
4. `site_base_url` 为空 vs 设值两种部署路径(根域 vs 项目子路径)下的链接正确性。

## 五、脚本用途一览(速查)

| 脚本 | 一句话职责 | 阶段 |
|---|---|---|
| `common.py` | 路径/配置/JSON/registry/topic_brief 的公共底座 | 全部 |
| `logs.py` | ghresearcher 事件文本 → 结构化仓库事件 | daily |
| `gh.py` | 包 `gh`/`ghresearcher`:`run`/`search_repos`/`repo_meta`/`fetch_readme`/`safe_repo_meta` | daily, search, merge |
| `daily.py` | 每日免费元数据流 → 候选表 Issue | daily |
| `search.py` | 多查询 Union 去重 → `data/search` | ① |
| `merge.py` | daily+search 汇池,new/updated/seen 分流 | ② |
| `agent.py` | OpenAI 兼容 LLM 层(`score_repo`/`build_code_card`,env 取密钥,重试) | ③⑤ |
| `score.py` | 并发 README 打分 + 回写 registry | ③ |
| `archive.py` | keeper 浅克隆 + 三源 wiki 归档,重试+低并发 | ④ |
| `cards.py` | keeper 生成 4 段富卡片 | ⑤ |
| `issue.py` | 分组排序 → Issue 正文 + CSV | ⑥ |
| `build_site.py` | cards→静态站(首页/仓库页/归档页) | site |
| `run_weekly.sh` | 顺序编排每周 6 步(所有模块的接线图) | 编排 |
